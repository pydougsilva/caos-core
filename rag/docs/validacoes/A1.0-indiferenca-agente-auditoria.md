# A1.0 — Auditoria da Proposta de Indiferença de Agente

---

## RESUMO EXECUTIVO

A proposta "C.A.O.S v6.0 — Indiferença de Agente / Runtime Institucional" contém
um insight arquitetural genuíno envolvido em premissas técnicas incorretas e uma
nomenclatura que contradiz o que a proposta realmente implementa.

**Veredicto:** INCORPORAÇÃO PARCIAL com correções estruturais obrigatórias.

O insight válido: "é necessário um mecanismo para garantir que cada ferramenta
CARREGUE EFETIVAMENTE o protocolo canônico AGENTS.md."

O que a proposta chama de "indiferença": é na verdade "configuração paralela por ferramenta" —
o oposto do que o C.A.O.S v5.0 conquistou com a separação "papéis sobre identidades".

**Conflito estrutural central:** a proposta reintroduz dependência nominal de ferramentas
(`.claude/`, `.codex/`) no nível de infraestrutura — exatamente o que foi eliminado em v5.0.

## ETAPA 2 — AUDITORIA EXPERIMENTAL

### 2.1 Análise do Mecanismo de Carregamento por Ferramenta

#### Claude Code for VS Code — Achado Crítico

**Claim da proposta:** "a extensão carrega automaticamente `.claude/instructions.md`"

**Verificação empírica (2026-05-28):**
```
afetoeforma/.claude/: settings.local.json  ← único arquivo presente
caos-core/.claude/:   AUSENTE              ← diretório não existe
CLAUDE.md:            AUSENTE em ambos os repositórios
```

**Conclusão:** A claim é FACTUALMENTE INCORRETA.

Claude Code lê `CLAUDE.md` (arquivo na raiz do projeto ou nos diretórios pai) — não
`.claude/instructions.md`. O diretório `.claude/` armazena configurações operacionais
(`settings.json`, `settings.local.json`) — não instruções de protocolo.

Evidência: o próprio ambiente operacional do C.A.O.S não tem `CLAUDE.md` nem
`.claude/instructions.md`. A continuidade institucional é obtida via AGENTS.md
carregado manualmente a cada sessão — o que é, aliás, o comportamento correto
segundo o princípio de isolamento de sessão (P9).

**Implicação para o teste:** Se o teste "passar" para Claude Code, o agente estaria
seguindo o protocolo por razões diferentes das declaradas (AGENTS.md carregado
manualmente, memória de sessão, instrução implícita na descrição da tarefa) —
configurando um FALSO POSITIVO estrutural.

---

#### Codex CLI — Análise

**Claim da proposta:** "`.codex/config.toml` é respeitado pela extensão oficial"
e "CLI aceita `--instructions .codex/instructions.md`"

**Verificação:** Impossível verificar empiricamente sem executar o CLI.

**Avaliação por plausibilidade:**
- `codex --instructions .codex/instructions.md "tarefa"`: PLAUSÍVEL para CLI tools
- `.codex/config.toml` carregado automaticamente pela extensão VSCode: INCERTO

**Incerteza estrutural:** A proposta não cita documentação oficial do Codex CLI para
confirmar esses comportamentos. Sem confirmação, o teste tem risco de falso negativo
(ferramenta não carrega o arquivo que se assume que carrega).

### 2.2 Validade do Teste Mínimo

#### O que o teste realmente mede vs. o que afirma medir

| Dimensão | O que o teste AFIRMA medir | O que o teste REALMENTE mede |
|---|---|---|
| Hipótese central | "indiferença de agente" via instruções compartilhadas | "cada ferramenta consegue seguir suas próprias instruções" |
| Fonte das instruções | um protocolo compartilhado | DOIS arquivos com conteúdo duplicado |
| Agente "indiferente" | qualquer ferramenta, mesma fonte | cada ferramenta, fonte própria |

#### Critérios de sucesso — como declarados vs. como deveriam ser

**Conforme a proposta:** ambos devem produzir proposta → aprovação → execução → snapshot → telemetria.

**Problema:** Esse critério não distingue entre:
- "O agente seguiu as instruções do arquivo de configuração"
- "O agente seguiu suas instruções de sessão preexistentes"
- "O agente inferiu o formato correto a partir da descrição da tarefa"
- "O agente é suficientemente avançado para estruturar respostas assim por padrão"

Um agente LLM avançado sem NENHUMA instrução específica tende a estruturar respostas
de forma similar ao protocolo C.A.O.S quando a tarefa usa linguagem institucional.
Isso é um falso positivo por design.

#### Critérios de sucesso válidos (proposta de correção)

Para provar indiferença de agente via instrução universal:

```
PRECONDIÇÃO: Nenhum arquivo de instrução carregado (sem AGENTS.md, sem CLAUDE.md,
             sem .claude/instructions.md, sem session history com o protocolo)

TAREFA IDÊNTICA: enviada a Claude Code e Codex CLI sem contexto adicional

MÉTRICAS:
□ O agente produziu proposta estruturada com campos: Objetivo, Passos, Impacto?
□ O agente aguardou aprovação explícita antes de executar?
□ O agente gerou snapshot com timestamp e sumário?
□ O agente gerou telemetria no caminho correto?
□ O formato de saída é idêntico entre os dois agentes?
□ O resultado seria indistinguível para um terceiro avaliador?

CONTROLE: mesma tarefa sem instruções de protocolo → os dois agentes produzem saída DIFERENTE?
Se sim, as instruções fazem diferença. Se não, as instruções são ineficazes.
```

#### Falsos Positivos confirmados

1. **FP1 — Claude Code com path errado**: Claude Code não lê `.claude/instructions.md`.
   Se passa, é porque seguiu AGENTS.md ou session context — não o arquivo declarado.

2. **FP2 — Instrução implícita na tarefa**: A tarefa de teste usa linguagem institucional
   ("seguindo o protocolo obrigatório") que induz qualquer LLM avançado a seguir o formato.

3. **FP3 — Convergência natural de LLMs**: LLMs avançados (Claude, Codex, GPT-4) tendem
   a produzir outputs estruturalmente similares para tarefas similares, independentemente
   de instruções específicas.

#### Falsos Negativos possíveis

1. **FN1 — Codex não carrega `.codex/config.toml`**: se a extensão não suporta auto-load,
   o teste falha por motivo técnico não relacionado à hipótese.

2. **FN2 — Variação de formato**: agentes podem seguir o PROTOCOLO mas gerar formatos
   diferentes (snapshot como JSON vs. Markdown), causando falha por critério superficial.

---

### 2.3 Verdict Experimental

**O teste mínimo proposto:**
- É INVÁLIDO como prova de "indiferença de agente"
- É ÚTIL como smoke test de "cada ferramenta pode carregar suas próprias instruções"
- Tem alto risco de FALSO POSITIVO para Claude Code (path incorreto)
- Tem INCERTEZA para Codex CLI (comportamento do extension não documentado)
- Não tem GRUPO DE CONTROLE para distinguir compliance das instruções vs. inferência LLM

**Antes de executar o teste:** corrigir o path do Claude Code para `CLAUDE.md`.

### 3.2 Grau de Inovação

#### Dentro do C.A.O.S

**Baixo.** O conceito de "protocolo nos artefatos, não na ferramenta" já existe em v5.0
como princípio P14 (papéis sobre identidades). A novidade é a **camada de adapter**
que garante carregamento efetivo do protocolo — isso é OPERACIONAL, não inovação conceitual.

#### Frente ao mercado de AI tooling

**Baixo-Médio.** Multi-agent coordination com shared instructions é resolvido por:
- LangChain/LangGraph (orchestration com shared state)
- AutoGen (multi-agent conversations)
- CrewAI (role-based agents)

O diferencial C.A.O.S não está na coordenação técnica — está na **governança institucional**
(human gate, snapshots como memória, continuidade cognitiva). Isso o proposta não captura.

#### Frente a agentic frameworks

A proposta replica em shell scripts o que frameworks já fazem em código.
A proposta NÃO replica o que o C.A.O.S tem de único: lineage, governance, institutional memory.

**O real diferencial perdido:** a proposta foca em "como invocar os agentes" em vez de
"como preservar o que os agentes aprenderam" — que é a proposta de valor do C.A.O.S.

### 3.5 Riscos Arquiteturais

**R1 — Lock-in nominal (severidade: ALTA)**
Arquivos `.claude/` e `.codex/` criam dependência de nomes de fornecedores no nível
de infraestrutura. Viola P14. Cada mudança de ferramenta requer nova configuração.
Mitigação proposta: renomear para `.caos/adapters/claude.md`, `.caos/adapters/codex.md`
(namespace do sistema, não do fornecedor).

**R2 — Duplicação de source of truth (severidade: ALTA)**
Dois arquivos com o mesmo protocolo = duas fontes de verdade.
Quando o protocolo muda, ambos devem ser atualizados. Drift é inevitável.
Mitigação: adapters REFERENCIAM AGENTS.md, não DUPLICAM o protocolo.

**R3 — Complexidade operacional (severidade: MÉDIA)**
Script orchestrate.sh + adapter-claude.sh + adapter-codex.sh + adapter-generic.sh +
runtime.lock + queue.json = infraestrutura de software que precisará de manutenção.
Viola P6 (simplicidade operacional).
Mitigação: mínimo viável = APENAS adapters simples + CLAUDE.md. Scripts são v7.0.

**R4 — Fragmentação de estado (severidade: MÉDIA)**
`.caos/runtime.lock` e `.caos/queue.json` introduzem estado operacional fora do Git.
Conflita com o princípio de evidência verificável (v3.5).
Mitigação: usar Git como ledger para estado de execução (é o que o C.A.O.S já faz).

**R5 — Falsa indiferença (severidade: MÉDIA)**
O sistema parece "indiferente" mas exige N arquivos de configuração para N ferramentas.
Um novo agente (Cursor) exige novo adapter — não há verdadeira indiferença.
Mitigação: um único `CLAUDE.md` ou `AGENTS.md` que qualquer agente pode ler é mais próximo
de verdadeira indiferença do que N arquivos de configuração.

**R6 — Burocracia por tarefa (severidade: BAIXA-MÉDIA)**
Script orchestrate.sh que exige arquivo YAML de task, espera aprovação, coleta snapshot...
adiciona burocracia ao ciclo operacional sem ganho proporcional se o usuário já é o gate.
Mitigação: o humano já é o orquestrador — o script duplica papel humano.

## ETAPA 5 — PACOTE PARA REVISÃO DO CODEX

### Contexto para o Codex (leitura independente)

O C.A.O.S é uma infraestrutura cognitiva local para desenvolvimento assistido por IA.
Sua proposta de valor central: **continuidade institucional entre sessões efêmeras**.

O sistema atingiu v5.0 com:
- 24 módulos /r (regras) + 10 módulos /k (conhecimento)
- Protocolo de ciclo em 10 etapas com gate humano obrigatório
- 15 princípios fundamentais formalizados
- Separação caos-core (infraestrutura reutilizável) ↔ afetoeforma (produto)

A proposta auditada propõe uma nova direção: "Indiferença de Agente" — tornar qualquer
agente de IA um runtime intercambiável que segue o mesmo protocolo institucional.

### Perguntas abertas para o Codex avaliar independentemente

1. **P14 é inviolável?**
   A auditoria classificou a proposta como violação de P14 (papéis sobre identidades).
   O Codex concorda? Existe leitura alternativa onde `.caos/adapters/claude.md` não
   viola P14 mas ainda atende ao objetivo de garantir carregamento do protocolo?

2. **O script orchestrate.sh é prematuro?**
   A auditoria classificou-o como v7.0. O Codex discorda? Existem casos de uso imediatos
   onde o script agregaria valor proporcional ao custo de manutenção?

3. **CLAUDE.md vs. AGENTS.md como source of truth para Claude Code**
   A auditoria sugere CLAUDE.md como adapter que referencia AGENTS.md.
   Alternativa: tornar AGENTS.md o CLAUDE.md (renomeá-lo). Qual é a abordagem correta?
   Implicação: AGENTS.md é o formato canônico do C.A.O.S para múltiplos agentes;
   CLAUDE.md é o formato específico do Claude Code. Conflito ou complementaridade?

4. **State management sem Git é realmente um conflito com o C.A.O.S?**
   `.caos/runtime.lock` como arquivo temporário (em .gitignore) pode ser compatível com
   o modelo Git-as-ledger se o lock for efêmero e não rastreado. O Codex avalia como
   conflito, compatível ou neutro?

5. **A proposta resolve o problema correto?**
   O problema real que a proposta tenta resolver: "cada sessão perde contexto, regras e decisões."
   O C.A.O.S v5.0 já resolve isso via AGENTS.md + snapshots + telemetria.
   O que a proposta adiciona é: "garantir que o agente CARREGUE o protocolo automaticamente."
   Isso é um problema real que vale uma nova camada arquitetural? Ou é um problema de processo
   (usuário não carrega AGENTS.md) que não requer infraestrutura adicional?
